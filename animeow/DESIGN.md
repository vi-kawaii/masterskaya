# DESIGN.md — animeow

Документ фиксирует жанр, стек, архитектуру и план разработки.
Обновляется по мере движения. Отметки статуса: [ ] — не сделано,
[~] — в работе, [x] — сделано.

1. Что это за игра
   Открытый 3D-мир в духе GTA / Genshin, от третьего лица.

Бесшовный открытый мир с чанковым стримингом.

TPS-камера с орбитой, зумом, коллизией.

Полный locomotion-набор: ходьба, бег, спринт, прыжок, падение,
приземление. Позже — лазание, плавание, глайд.

Гибридный бой: огнестрел + ближний бой + скиллы.

Транспорт (Vehicle) с механикой «сел / вышел».

NPC с AI, диалогами, квестами.

Инвентарь, прогрессия, save/load.

Полноценный UI: меню, HUD, карта, квест-лог, инвентарь, диалоги.

Масштаб на старте: маленький регион (~2×2 км), потом расширяем.

4. Ключевые подсистемы
   4.1. Мир
   Чанки фиксированного размера (например, 64×64 м).

Каждый чанк — glTF/GLB-сцена + метаданные (NPC, спавны, триггеры).

Активны только чанки вокруг игрока + буфер. Остальные выгружаются.

LOD для дальних объектов.

Освещение: DirectionalLight + динамические источники, тени в ближней зоне.

**Рельеф и ходьба по нему.**
- Слоны: `MoveAndSlideConfig::max_slope_angle`. По умолчанию ~45°.
  Круче — персонаж скользит. Настраивается под геймплей.
- Ступеньки: автоподъём через raycast вперёд-вниз (`max_step_height`).
  Позже, когда появятся лестницы.
- Спуск без отрыва: `snap to ground` — если после движения вниз земля
  близко, прилипаем. Иначе на спуске персонаж «отрывается».
- Рельеф: гибрид — крупные формы дизайнер лепит в Blender, детали
  (трава, камни) — процедурно. Формат пока не зафиксирован.

4.2. Персонаж
Кинематический контроллер на avian3d (`RigidBody::Kinematic` +
`CustomPositionIntegration` + `MoveAndSlide`).

Ввод: WASD относительно направления камеры, спринт, прыжок, гравитация.

Состояния locomotion: idle / walk / run / sprint / jump / fall / land.

Поворот: плавный Quat::slerp в сторону движения.

Grounded — через cast_move из центра капсулы вниз.

**Разделение физики и визуала.** Капсула (`RigidBody::Kinematic`)
несёт трансформ позиции. Модель — её ребёнок, вращается отдельной
системой `rotate_model_towards_movement` через `Quat::slerp`. Физика
никогда не крутится — только визуал.

4.3. Камера
CameraRig (родитель) + Camera3d (ребёнок).

Yaw/pitch от мыши, зум колесом, коллизия через raycast.

Сглаживание позиции и поворота.

Режимы: TPS-свободный, TPS-прицеливание, FPS-прицеливание.

**Сглаживание — только ввод, не слежение.**
- Риг жёстко привязан к игроку + `EYE_HEIGHT`. Без `lerp` по позиции —
  иначе укачивает.
- Мышь двигает *целевые* yaw/pitch (`target_yaw`, `target_pitch`),
  система `orbit_camera` плавно ведёт текущие значения к целям через
  `alpha = 1 - exp(-k·dt)`. Зум — так же через `target_distance`.
- Ощущение: «мышь тянет камеру с лёгкой инерцией», как в Genshin.

4.4. Бой
Гибрид: огнестрел (hitscan + снаряды) + ближний бой + скиллы.

Оружие — компонент: Weapon { damage, cooldown, range, ammo, kind }.

Скиллы — компонент: Ability { cooldown, cost, effect }.

Элементы/статусы — позже.

4.5. Транспорт
Физика: raycast-vehicle на avian3d.

Механика «сел / вышел»: переключение управляемой сущности.

Камера переключается между режимами.

Типы: машина → потом мото, лодка и т.д.

State machine: idle / patrol / alert / chase / attack / flee / talk.

Навигация: waypoint/сетка → позже navmesh.

Толпы: спавн/деспавн по чанкам.

Диалоги: система + UI + стейт Dialog.

9. Журнал решений
   Короткие записи, почему сделано именно так. Не удалять — контекст.

Loading через bevy_asset_loader. Таймер убран. LoadingState сам
переключает GameState, когда ассеты загружены. Это соответствует
ARCHITECTURE.md §«Loading — это стейт, а не таймер».

Кинематический контроллер через avian3d MoveAndSlide.
RigidBody::Kinematic + CustomPositionIntegration: avian решает
коллизии (sweep + slide), но не двигает тело сам — Transform меняем
мы. Линейную скорость храним в LinearVelocity, обновляем в
character_movement. Так сохраняется полный контроль над движением,
что и заявлено в §4.2.

Grounded через cast_move, а не cast_ray. Стреляем из центра
капсулы вниз на 0.95 м (полвысоты капсулы 0.9 + запас). Раньше
использовали cast_ray из точки translation - 1.0 — это было ниже
низа капсулы и не находило пол.

Пол должен быть RigidBody::Static + Collider. Изначально пол был
только визуалом (Mesh3d(Plane3d)) без коллайдера, из-за чего
move_and_slide не находил землю и игрок падал в −∞.

Модель персонажа — WorldAssetRoot как ребёнок физической капсулы.
Родитель несёт RigidBody::Kinematic + Collider::capsule + Transform,
им управляет character_movement. Ребёнок — только визуал
(WorldAssetRoot + локальное смещение по Y). Так физика и визуал
развязаны: коллайдер не зависит от размеров модели, а модель можно
двигать/масштабировать/поворачивать локально, не трогая физику.
Bevy 0.19: Scene → WorldAsset, SceneRoot → WorldAssetRoot.

Папка ассетов — assets/, не art/. Bevy по умолчанию ищет ассеты в
<CARGO_MANIFEST_DIR>/assets. Если назвать папку иначе (art/, models/),
нужно переопределять AssetPlugin.file_path. Проще следовать
соглашению движка. Исходники моделей (Blender-проекты) при необходимости
держать отдельно, например в art-src/.

**Разворот модели — отдельная система, не в character_movement.**
`rotate_model_towards_movement` читает `DesiredYaw` (пишется в
character_movement, только когда есть ввод) и крутит `Transform`
ребёнка-модели через `Quat::slerp` с FPS-независимым сглаживанием
(`alpha = 1 - exp(-k·dt)`). Крутить родителя-капсулу нельзя —
коллайдер круглый, но вращение добавляет работу в физике и
завязывает sweep на rotation. Физика — только translation, визуал —
свой rotation. Порядок через `.chain()`: сначала движение, потом
разворот.

**Камера — плавность во вводе, не в слежении.** Сглаживание
слежения (`lerp` позиции рига к игроку) даёт эффект «укачивания» и
смотрится «по-инди», не к месту. Плавность нужна в ощущении мыши:
мышь двигает `target_yaw`/`target_pitch`, система `orbit_camera`
ведёт текущие значения к целям через `alpha = 1 - exp(-k·dt)`. Риг
при этом **жёстко** привязан к игроку (`follow_player` без lerp).
Так камера «тянется» за мышью, как в Genshin, но не «отстаёт» от
игрока. Зум — через тот же сглаживатель (`target_distance`).
`camera_smoothing = 25.0` (1/с), подстраивается по ощущению.

**Разделение «текущее / цель» в CameraRig.** `yaw/pitch/distance` —
что видно на экране сейчас; `target_yaw/target_pitch/target_distance`
— куда мышь «тянет». Это позволяет сглаживать ввод, не сглаживая
позицию рига. Смешивать нельзя — иначе либо укачивает, либо мышь
«прилипает».

**Модель — самодостаточная, без компенсаций в коде.** Модель
приведена к правилам Bevy ещё в Blender:
- Metric, Meters, Scale 1.0.
- Высота 1.8 м по Z (под капсулу `Collider::capsule(0.4, 1.0)`).
- Origin между ступней, по центру X/Y.
- Forward в `-Y` в Blender = `+Z` в Bevy (Blender Z-up → glTF Y-up
  даёт маппинг: Blender(X,Y,Z) → glTF(X, Z, −Y), значит −Y Blender
  → +Z glTF).
- Rotation/scale/location применены (`Ctrl+A → All Transforms`).
- Empty между арматурой и мешами убраны, трансформы схлопнуты.

Тогда `MODEL_YAW_OFFSET = 0.0` в коде — никакой магии. Следующая
модель по тем же правилам заведётся без правок. Раньше была
константа `+PI/2`, компенсирующая исходный поворот — теперь этого
нет.

**Отладочный визуал коллайдеров — через PhysicsDebugPlugin.** avian3d
умеет рисовать коллайдеры линиями. Это даёт мгновенную визуальную
проверку размеров капсулы, пола и любых препятствий. На ранних
этапах важнее видеть коллизии, чем экономить FPS. Для релиза —
обернуть в `#[cfg(debug_assertions)]` или фиче-флаг.

**Открытый вопрос: как поставлять карту.** Два подхода:
- Простой: плоская земля + отдельные статические коллайдеры на
  холмы/стенки/объекты. Быстрый старт, подходит для отладки
  контроллера.
- Правильный: чанки 64×64 м, каждый со своим мешем + коллайдером
  (обычно `Collider::trimesh` для ландшафта). Стриминг по радиусу.

Начинать — с простого (debug-полигон), к чанкам переходить после
того, как контроллер стабильно ходит по склонам и ступенькам.
